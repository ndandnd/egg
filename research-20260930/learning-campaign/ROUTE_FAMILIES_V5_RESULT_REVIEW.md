# Recovery and replay review

**Verdict:** I found no material blocker to handing off these results with the stated scope and numerical qualification. This review checks receipts, provenance, accounting, backup coverage, replay code and report consistency; it does not rerun training or the full replay.

The nine originally failed tasks (0, 1, 4–9, 11) completed in recovery array 722702. Their wrapper and task receipts agree on completion, and each runtime record shows successful XGBoost and CatBoost imports, a native tiny fit, and frozen training without timeout or signal. The original three successful tasks remain in array 720831. Recovery task identity preserves the original fold, seed, pool and exact 18 frozen source hashes; the replay additionally checks the three recovery source hashes and stage/stream hashes. Scoped accounting records all 12 original and nine recovery task rows by array, task ID, user, job name and submission time: 1,784 elapsed task-seconds and 1,973 allocated CPU-seconds combined, including the original failures. This identity check excludes unrelated records from earlier reuse of an array job ID.

The recovery manifest covers exactly 405 files across the nine completed tasks: 1,147,974,327 raw bytes packaged into 455,084,392 archive bytes. The archive script reads back each member and compares size and SHA256, checks duplicate/member coverage and fails with explicit errors. The manifest records raw preservation on local and remote storage; the backup README gives repository-relative restore instructions. The separate Slurm-log receipt records all 18 log paths and hashes, including empty stderr files.

The replay JSON’s script hash matches the reviewed replay source. Its numerical status is appropriately qualified: the initial probability check at absolute and relative tolerance 1e-8 failed and remains recorded. The first failure is XGBoost task 0, outer row 4833 (`physical_v2_s10020/source0/in_T16`): saved 0.5488070249557495 versus native 0.5488070845603943, a one-float32-ULP difference. Across tasks, XGBoost differs by at most two float32 ULPs (1.1920929e-7); the JSON separately marks exact all-family probability reproduction false. The verifier confirms complete source rankings, fixed-0.5 decisions, candidate choices and inner family promotion are unchanged. Metrics recomputed from saved probabilities meet the declared 1e-12 check; native-versus-saved XGBoost source log-loss and Brier differences peak at 3.34e-10 and 1.60e-10. The results report explains these limits rather than describing the probabilities as bitwise identical.

The headline table agrees with the JSON’s equal-timetable aggregates (for example, XGBoost full-cohort log loss/AP/top-k are 0.0694165/0.8282705/0.6966855; CatBoost is 0.0692983/0.8264842/0.6977480). The report also states the limits that matter for interpretation: this is movement membership in observed feasible incumbents, not optimal-route identification; top-k is a ranking diagnostic, not a decoder; the 128 timetables share a repeatedly explored TRAIN bank rather than an independent final test; one source remains censored; and no fleet-cost or solving-speed claim follows from these scores. Its proposed next step separates prediction from decoding, charging and global verification.
